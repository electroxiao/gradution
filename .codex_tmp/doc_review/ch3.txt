[P:Heading 1] 第3章 大模型与知识图谱融合的智能助学系统设计

[P:Normal] 本章主要对基于大模型与知识图谱的自适应编程作业辅导系统进行系统分析与总体设计。系统面向编程课程教学场景，围绕学生学习过程中的答疑、练习、作业提交、自动判题和薄弱点识别等环节展开设计，旨在为学生提供更具针对性的学习支持，同时为教师提供掌握学生学习状况、维护课程知识体系和管理编程作业的工具。通过大模型、知识图谱、自动判题和数据统计等功能的结合，系统能够将学生的提问记录、作业结果和知识点掌握情况进行整合，为后续的个性化辅导和教学决策提供数据基础。

[P:Heading 2] 3.1 需求分析

[P:Normal] 本系统的主要用户包括学生和教师两类角色。学生主要通过系统进行编程知识问答、作业查看、代码提交和薄弱点训练。教师主要通过系统进行作业发布、学生学习数据查看、知识图谱维护和教学情况分析。系统在满足基本教学管理需求的同时，还需要结合大模型与知识图谱技术，提高编程学习辅导的针对性和智能化水平。

[P:Heading 3] 3.1.1 需求概述

[P:Normal] 根据系统的应用场景和用户角色，本系统主要包括以下几个方面的需求。

[P:Normal] （1）大模型答疑功能。学生在学习 Java 编程知识或完成作业过程中，可以通过聊天页面向系统提出问题，系统直接调用大模型生成回答，为学生提供较为准确、连贯的解释与辅导内容。回答完成后，系统再在后台抽取本轮问答涉及的知识点，用于学习记录和统计分析。

[P:Normal] （2）提问知识点记录功能。系统需要对学生提问过程中涉及的知识点进行记录，用于形成学生学习轨迹。教师可以根据提问记录了解学生近期关注或疑问较多的知识内容。提问知识点记录用于学习轨迹回看和教师端提问热点统计。

[P:Normal] （3）作业管理功能。教师可以在系统中创建编程作业，设置题目内容、测试用例和截止时间，并将作业发布给指定学生。学生可以在作业页面查看作业要求并提交 Java 代码。

[P:Normal] （4）自动判题功能。学生提交代码后，系统需要在隔离的 Docker 沙箱环境中运行代码，并根据教师设置的测试用例进行自动判题，返回运行结果、通过情况和错误信息，帮助学生及时发现代码问题。

[P:Normal] （5）数据统计功能。系统需要对学生的提问记录、作业完成情况、判题结果和薄弱知识点进行汇总统计，为教师掌握班级整体学习情况和单个学生学习状态提供数据支持。

[P:Normal] （6）图谱编辑功能。教师可以维护系统中的知识图谱，包括知识点结点和知识点关系的新增、修改、删除与查看。知识图谱作为答疑后知识点抽取、薄弱点推荐和题目知识点绑定的重要基础，需要支持教师根据课程内容持续更新。

[P:Heading 3] 3.1.2 功能性需求分析

[P:Heading 3] 3.1.3 非功能性需求分析

[P:Normal] 除功能性需求外，系统还需要满足一定的非功能性需求，以保证系统在实际教学场景中能够稳定、可靠、方便地运行。结合本系统的应用特点，非功能性需求主要包括以下几个方面。

[P:Normal] （1）易用性需求。系统界面应简洁清晰，学生能够快速完成提问、查看作业和提交代码等操作，教师能够方便地发布作业、查看统计数据和维护知识图谱。对于作业判题结果、薄弱点提示和图谱信息，系统应采用直观的页面展示方式，降低用户理解和操作成本。

[P:Normal] （2）安全性需求。系统需要对学生和教师用户进行身份认证，并根据用户角色限制功能访问范围。学生只能查看和提交与自己相关的作业，教师只能进行教学管理相关操作。同时，系统应避免敏感配置泄露，保证数据库连接信息、大模型接口密钥等内容不暴露在前端或公共代码中。

[P:Normal] （3）可靠性需求。系统应保证核心业务流程稳定运行，包括用户登录、大模型答疑、作业发布、代码提交和自动判题等功能。在外部服务异常或代码运行失败时，系统应返回明确的错误提示，避免因异常中断影响用户继续使用。

[P:Normal] （4）性能需求。系统应能够在常见教学场景下保持较好的响应速度。普通页面查询、作业列表加载和统计数据展示应在较短时间内完成；大模型答疑和代码判题由于涉及外部模型调用或 Docker 沙箱执行，系统应设置合理的超时时间，避免长时间阻塞。

[P:Normal] （5）可维护性需求。系统应采用前后端分离结构，后端按照路由、模型、服务层和数据访问逻辑进行划分，前端按照页面、组件和接口封装进行组织。清晰的模块划分有利于后续功能扩展和问题定位，例如新增作业类型、扩展知识图谱关系或调整统计维度时，能够减少对其他模块的影响。

[P:Normal] （6）隔离性需求。由于系统涉及学生提交代码的执行，代码运行必须在 Docker 沙箱环境中完成，并限制网络、内存、CPU 和运行时间，避免学生代码对服务器环境造成影响。自动判题模块不能直接在宿主机环境中执行用户提交的代码。

[P:Heading 2] 3.2 系统总体架构设计

[P:Normal] 系统整体由用户交互层、业务服务层、数据存储层和外部服务层组成，其总体架构如图3-2所示。

[P:表格配文] 图3-2 系统总体架构图

[P:Normal] （1）用户交互层

[P:Normal] 面向学生和教师两类用户。学生端提供答疑、作业提交、薄弱知识点查看和针对性训练等功能。教师端提供作业管理、学情统计和知识图谱维护等功能。通过区分不同角色的使用场景，系统能够分别满足学生个性化学习和教师教学管理的需求。

[P:Normal] （2）业务服务层

[P:Normal] 是系统的核心处理部分，主要负责用户认证、问答处理、作业管理、自动判题、薄弱点推荐与训练、学情统计和图谱维护等任务。系统通过身份认证与权限控制机制识别学生和教师角色，并限制不同角色可访问的页面和接口。答疑模块负责接收学生提问、调用大模型生成回答，并在回答完成后异步抽取本轮问答涉及的已有知识点。作业模块负责作业创建、题目维护、学生提交记录和判题结果管理。自动判题模块负责对学生提交内容进行评测，并在提交结果未通过时，依据题目绑定知识点更新学生未掌握薄弱点。薄弱点推荐与训练模块负责展示学生当前薄弱知识点，并结合知识图谱生成相关知识点推荐和针对性训练内容。知识图谱维护模块负责维护知识点结点及其关系，为答疑知识点记录、薄弱点推荐和作业知识点绑定提供基础数据支持。

[P:Normal] （3）外部服务层

[P:Normal] 主要包括大模型服务和 Docker 沙箱环境。大模型服务用于完成学生问题回答、作业辅导和知识点描述生成等任务；Docker 沙箱用于隔离执行学生提交的 Java 代码，并通过限制网络、内存、CPU 和运行时间提高代码判题过程的安全性。系统通过业务服务层统一调用外部服务，从而降低不同模块之间的耦合度。

[P:Normal] （4）数据存储层

[P:Normal] 采用 MySQL 与 Neo4j 相结合的方式。MySQL 主要保存用户信息、作业信息、提交记录、薄弱知识点状态和题目知识点绑定等结构化业务数据。Neo4j 用于存储知识图谱，包括知识点结点与知识点依赖关系。通过关系型数据库与图数据库的配合，系统既能保证业务数据的稳定存储，又能支持知识结构的关联查询和可视化展示。

[P:Normal] 通过上述架构设计，系统将学生学习过程中的提问、作业提交、错题知识点和教师图谱维护连接起来，使学习行为能够转化为可记录、可分析和可反馈的数据，为后续功能实现提供了基础。

[P:Heading 2] 3.3 业务流程设计

[P:Normal] 不同用户在系统中的业务目标和操作内容有所不同。教师端主要围绕作业管理、学习情况查看和知识图谱维护展开。学生端主要围绕作业完成、智能答疑和薄弱点训练展开。系统业务流程图如图3-3所示。

[P:表格配文] 图3-3 系统业务流程图

[P:Normal] （1）教师端业务流程

[P:Normal] 教师登录系统后，可以根据教学安排创建和发布作业。为了使作业结果能够与学生知识掌握情况建立联系，教师在创建题目时可以为题目绑定相关知识点。作业发布后，学生可以完成对应作业，系统会记录学生的提交情况和判题结果。

[P:Normal] 在作业发布后，教师可以查看学生的作业完成情况。同时，系统会对学生的薄弱点和提问涉及的知识点进行统计，并形成排行榜展示。教师可以通过这些统计结果发现学生在学习过程中的共性问题，从而为后续教学讲解、作业设计和个别辅导提供参考。

[P:Normal] 此外，教师还可以对知识图谱进行编辑维护。教师可根据课程内容、知识点变化或实际教学需要，对图谱中的知识点及其关系进行调整，使系统中的知识结构更加符合当前教学场景。

[P:Normal] （2）学生端业务流程

[P:Normal] 学生登录系统后，可以查看并完成教师发布的作业。系统会对学生提交的作业进行自动判题，记录作业提交结果。当学生题目作答错误时，该题目所绑定的知识点会被记录为学生的薄弱点，用于后续学习分析和训练推荐。

[P:Normal] 针对系统记录的薄弱点，学生可以进入薄弱点训练模块进行针对性练习。通过围绕薄弱知识点进行训练，学生能够有目的地巩固相关内容，从而提高学习效果。

[P:Normal] 此外，学生可以随时通过智能答疑模块向大模型提问。系统会根据学生的问题生成回答，并记录本次提问涉及的知识点。这些记录不仅便于学生回顾自己的学习过程，也可以为教师了解学生关注较多或疑问较多的知识内容提供数据依据。

[P:Heading 2] 3.4 数据库设计

[P:Normal] 数据存储是本系统设计与实现中的关键环节。数据库负责存储系统中的用户数据、问答记录、作业数据、提交记录、知识点引用和薄弱点记录等重要信息，系统需要通过数据库查询获取用户学习过程、作业完成情况和知识点掌握状态等关键数据。基于系统业务特点，选择目前 Web 系统开发中常用且成熟的关系型数据库 MySQL 作为业务数据的持久化存储方案，用于保存用户、会话、作业、题目、提交记录和薄弱点等结构化数据。同时，系统使用图数据库 Neo4j 存储 Java 编程知识图谱。Neo4j 能够以节点和关系的形式组织知识点数据，适合表达知识点之间的前置、关联和层次关系，并能够支持答疑后知识点匹配、薄弱点推荐和教师端图谱维护等功能。本节将详细探讨系统的数据库设计方案，包括 MySQL 业务数据库的 E-R 图设计、Neo4j 知识图谱数据模型设计以及数据表设计。

[P:Heading 3] 3.4.2 Neo4j知识图谱设计

[P:Normal] Neo4j 是一种面向图结构数据的非关系型数据库，采用节点、关系和属性组织数据，适合存储具有复杂关联的数据对象。知识图谱通常由实体节点、关系边和属性信息组成，节点表示具体知识对象，关系表示知识对象之间的语义联系，属性用于描述节点或关系的具体信息。

[P:Normal] 本系统使用 Neo4j 存储 Java 编程知识图谱，图谱节点统一采用 Knowledge 标签表示知识点，节点属性包括知识点名称、知识点描述和所属章节。知识点之间采用 DEPENDS_ON 关系连接，表示知识点之间的依赖关系。知识图谱结构设计如表 3-6 所示。

[P:表格配文] 表3-6 知识图谱结构设计

[TABLE]
元素类型 | 名称 | 属性/方向 | 含义 | 说明
节点 | Knowledge | name | 知识点名称 | 唯一标识 Java 编程知识点
节点 | Knowledge | desc | 知识点描述 | 描述知识点含义
节点 | Knowledge | chapter | 所属章节 | 支持教师端图谱筛选、章节管理和作业知识点绑定
