[P:Heading 1] 第5章 系统测试

[P:Normal] 系统测试是验证系统设计与实现效果的重要步骤。前文已经完成了系统需求分析、总体设计、数据库设计以及主要功能模块的实现说明，本章将在此基础上对系统进行测试与分析。通过对学生端、教师端、知识图谱维护、智能问答、编程作业和代码沙箱评测等核心功能进行测试，验证系统是否能够满足预期设计目标，并检查系统在异常输入、权限控制和外部服务调用等场景下的处理能力。

[P:Heading 2] 5.1 测试方法

[P:Normal] 本文设计并实现的基于大模型与知识图谱的自适应编程作业辅导系统，涉及学生端智能问答、薄弱点识别、知识图谱推荐、教师端图谱维护、编程作业发布、学生代码提交与 Docker 沙箱评测等多个功能模块。由于系统同时调用 MySQL、Neo4j、大模型接口以及本地 Docker 环境，因此需要通过系统测试对各模块之间的数据交互和业务流程进行综合验证。

[P:Normal] 本章测试主要采用黑盒测试与灰盒测试相结合的方法。黑盒测试主要从用户使用角度出发，不关注系统内部代码实现，而是通过模拟教师和学生的实际操作流程，验证系统页面展示、接口响应、数据保存和业务结果是否符合预期。例如，学生登录后能否正常进入问答页面，教师能否创建并发布编程作业，学生提交代码后系统能否返回评测结果等，均属于黑盒测试的范围。

[P:Normal] 灰盒测试则在了解系统部分内部结构的基础上，对关键业务流程进行进一步验证。本系统中，部分功能不仅需要观察前端页面结果，还需要结合后端接口返回结果、MySQL 数据记录、Neo4j 图谱节点关系以及 Docker 沙箱执行状态进行判断。例如，在学生作业提交未通过时，系统是否能够根据题目绑定的知识点更新薄弱点记录；教师修改知识图谱后，相关节点与关系是否能够同步在 Neo4j 中正确保存；学生代码运行时是否始终在 Docker 沙箱中执行等，都需要采用灰盒测试方式进行验证。

[P:Normal] 通过黑盒测试与灰盒测试的结合，可以较全面地检查系统功能的完整性和业务逻辑的正确性。同时，针对用户权限、异常输入、代码执行安全等场景进行测试，也能够验证系统在异常情况下的处理能力，保证系统在实际教学场景中能够稳定、安全地运行。

[P:Heading 2] 5.3 单元测试

[P:Normal] 单元测试是系统测试中的基础环节，主要用于验证系统中相对独立的函数、服务方法或业务逻辑是否能够按照预期执行。与功能测试相比，单元测试更加关注后端内部逻辑的正确性，能够在不依赖完整前后端交互流程的情况下，对核心业务规则进行快速验证。本系统后端采用 pytest 测试框架编写单元测试，测试内容主要包括作业开放时间判断、作业提交状态处理、错题薄弱点更新、聊天知识点事件记录以及薄弱点图谱推荐等内容。

[P:Normal] 在本系统中，编程作业模块与学生薄弱点识别功能之间存在较强的业务关联。当学生提交编程题后，系统需要根据代码评测结果判断是否更新学生的薄弱点信息。若提交结果为 accepted，说明学生已通过该题，不应将题目绑定的知识点标记为薄弱点；若提交结果为 wrong_answer、runtime_error 等未通过状态，则系统需要读取该题绑定的知识点，并将相关知识点记录为学生的未掌握薄弱点。该逻辑直接影响后续的薄弱点推荐和针对性训练，因此本文选取作业错题薄弱点更新逻辑作为单元测试示例。

[P:Normal] 单元测试代码如表5-2所示。

[P:表格内容] 表5-2 单元测试代码样例

[TABLE]
from types import SimpleNamespace from unittest.mock import Mock, patch from backend.services.assignment_service import _mark_wrong_submission_bound_nodes_weak def _relation(relation_id: int, sort_order: int, node_id: int, node_name: str): return SimpleNamespace( id=relation_id, sort_order=sort_order, knowledge_node_id=node_id, knowledge_node=SimpleNamespace(id=node_id, node_name=node_name), ) def test_wrong_submission_marks_all_bound_nodes_weak_once() -> None: question = SimpleNamespace( knowledge_nodes=[ _relation(3, 2, 10, "数组"), _relation(1, 0, 20, "循环"), _relation(2, 1, 10, "数组"), ] ) submission = SimpleNamespace(status="wrong_answer") student = SimpleNamespace(id=1) db = Mock() with patch("backend.services.assignment_service.mark_node_weak") as mark_node_weak: _mark_wrong_submission_bound_nodes_weak(db, student, question, submission) assert [call.args for call in mark_node_weak.call_args_list] == [ (db, student, "循环"), (db, student, "数组"), ]

[P:Normal] 该测试用例通过 SimpleNamespace 构造模拟的题目、学生和提交记录对象，并使用 Mock 模拟数据库会话对象。测试中设置学生提交状态为 wrong_answer，同时为题目绑定“数组”和“循环”两个知识点，其中“数组”被重复绑定一次。执行薄弱点更新函数后，通过断言检查 mark_node_weak 方法的调用结果。测试结果表明，系统能够在学生提交错误答案时，将题目绑定的知识点标记为薄弱点，并且能够避免同一知识点被重复记录。

[P:Normal] 除上述测试外，系统还针对 accepted 状态提交、未绑定知识点的题目、作业开始时间和截止时间等边界情况编写了测试用例。例如，当提交状态为 accepted 时，系统不会调用薄弱点标记方法；当题目未绑定知识点时，系统不会产生无效的薄弱点记录；当作业尚未开始时，系统会拒绝学生提前提交。通过这些单元测试，可以有效验证后端核心业务逻辑在正常输入、异常输入和边界条件下的正确性，为后续功能测试提供基础保障。

[P:Heading 2] 5.4 功能测试

[P:Normal] 本章主要对基于大模型与知识图谱的自适应编程作业辅导系统进行了系统测试。首先说明了系统功能测试的测试内容和测试方法，然后围绕用户登录与权限控制、教师发布作业、学生完成作业、自动判题与薄弱点更新、学生通过大模型答疑、学生薄弱点推荐与针对性训练、教师学情分析与人工复核以及知识图谱维护等模块进行了测试。
