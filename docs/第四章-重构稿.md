## 4.5 基础支撑模块实现

基础支撑模块包括用户登录与权限控制和知识图谱维护两部分，为两条业务链路提供身份认证与知识底座支持。

### 4.5.1 用户登录与权限控制

系统面向教师和学生两类用户，不同角色登录后进入不同功能界面。登录功能采用前后端分离方式实现：前端基于 Vue 3 构建登录页面，使用 Pinia 保存当前用户状态；后端基于 FastAPI 提供登录、注册和用户信息查询接口。

用户登录流程如下：（1）用户在登录页面输入用户名和密码后，前端提交至 `/api/auth/login` 接口。后端查询 users 表并对密码进行哈希比对，若用户不存在或密码错误则返回失败提示。（2）校验通过后，后端生成访问令牌，将令牌、用户编号、用户名、角色和班级等信息返回前端。前端将令牌和角色存入 sessionStorage，根据角色跳转到对应页面。sessionStorage 按标签页隔离，支持同一浏览器中同时打开教师端和学生端。（3）后续访问时，前端通过 Axios 请求拦截器自动在请求头中携带令牌，后端解析令牌获取用户身份，对教师端接口额外校验角色。同时前端路由守卫根据角色限制页面访问。

### 4.5.2 知识图谱维护

知识图谱是第3章所述两条链路的共享知识底座。系统在教师端提供图谱可视化管理功能，教师可对知识点节点及其关系进行增、删、改、查操作。

系统使用 Neo4j 存储知识图谱主数据，MySQL 的知识点引用表（knowledge_nodes）保存节点名称、所属章节等引用镜像。教师在教师端图谱维护页面修改图谱后，系统同步更新 Neo4j 中的图数据和 MySQL 中的引用记录。

**图谱查询与展示。** 教师进入知识图谱管理页面后，前端向后端请求当前图谱数据。后端通过 Neo4j 查询 Knowledge 类型节点及其关系，核心 Cypher 查询如表4-1所示。

表4-1 图谱节点与关系查询

```
// 查询节点
MATCH (n:Knowledge)
RETURN n.name AS name, coalesce(n.desc, '') AS desc,
       coalesce(n.chapter, '') AS chapter, labels(n) AS labels
ORDER BY n.name ASC
LIMIT $limit

// 查询关系
MATCH (src:Knowledge)-[r]->(tgt:Knowledge)
RETURN src.name AS source, type(r) AS relation, tgt.name AS target
LIMIT $limit
```

前端收到节点和关系列表后，通过图谱画布组件进行可视化展示。系统支持按知识点名称、描述和章节标签进行搜索过滤。

**节点维护。** 教师可新增知识点节点或修改已有节点。新增节点时，系统通过 Neo4j 的 MERGE 操作创建 Knowledge 节点，避免重复创建。节点属性包括 name、desc 和 chapter。同时，系统同步维护 MySQL 中的知识点引用记录，确保作业题目绑定和薄弱点记录能正确引用该节点。

为减少教师手动编写知识点描述的工作量，系统提供大模型辅助生成描述功能。教师输入知识点名称后，后端构建提示词调用大模型生成 1 到 2 句中文描述，说明"这是什么"和"通常用来解决什么问题"。大模型返回后，教师可修改并确认保存。

**关系维护。** 教师可为两个知识点建立 DEPENDS_ON 关系。系统在创建关系时校验起点和终点，对关系名称进行规范化处理，通过 MERGE 操作避免重复创建。若输入的起点或终点知识点尚不存在，系统会自动创建对应节点。

## 4.6 错题驱动的诊断训练实现

本节对应第3章诊断训练链路的方法实现。按照业务顺序依次说明：教师发布作业并绑定知识点、学生提交作业、系统自动判题并更新薄弱点、薄弱点推荐与针对性训练。

### 4.6.1 作业发布与题目知识点绑定

教师可通过作业管理页面创建作业，设置标题、开始时间、截止时间和发布班级。作业题目支持选择题、填空题和编程题三类。编程题需配置初始代码、测试用例和判题方式。为减轻命题负担，教师可使用大模型辅助出题：输入出题要求和知识点，系统调用大模型生成题目初稿。

**题目知识点绑定。** 教师创建题目后，需为每道题绑定一个或多个知识图谱节点。系统支持教师手动搜索并绑定知识点，同时根据题目标题和题干在知识图谱中检索相关节点推荐绑定。题目与知识点的绑定关系保存至 assignment_question_knowledge_nodes 表，该表为题目和知识点之间的多对多关联表，结构如表4-2所示。

### 4.6.2 学生作业提交

教师发布作业后，被分配的学生可在学生端查看作业列表并进入作答页面。系统按题型展示不同作答区域：选择题以选项形式展示，填空题提供答案输入框，编程题提供在线代码编辑器。编程题作答区域引入 CodeMirror 编辑器，提供 Java 代码高亮、行号显示、括号匹配和自动缩进等功能，学生可直接在浏览器中编写代码。

### 4.6.3 多题型自动判题与薄弱点更新

自动判题是诊断训练链路的核心实现环节。学生提交作业后，系统通过后台任务异步执行判题，按题目类型分别处理。判题流程由 `_grade_pending_assignment_submission` 函数统一调度，核心逻辑如表4-3所示。

表4-3 判题调度核心逻辑

```
def _grade_pending_assignment_submission(db, submission_id):
    # 根据题目类型分派判题策略
    if question_type == "programming":
        status, results, ai_review, source = _grade_submission(...)
    elif question_type == "multiple_choice":
        status, results, ai_review, source = _grade_multiple_choice_locally(...)
    else:  # fill_blank
        ai_review = _run_ai_objective_review(...)
        status = _resolve_ai_only_status(question, ai_review)

    # 统一写入判题结果
    submission.status = status
    submission.results_json = results
    submission.ai_review_json = ai_review

    # 未通过则更新薄弱点
    _mark_wrong_submission_bound_nodes_weak(db, student, question, submission)
```

三种题型的判题策略如下。

**选择题**采用本地选项比对：将学生所选选项规范化后与教师设置的标准答案进行文本比对，一致则为 accepted，否则为 wrong_answer。

**填空题**调用大模型进行语义判分。系统将题干、标准答案、解析和学生答案组织为提示词，要求大模型以 JSON 格式返回判定结果。若大模型调用失败，回退到本地规范化比对。

**编程题**的判题过程最复杂，涉及沙箱执行和大模型评审两个阶段。编程题判题流程如图4-5所示。

```
图4-5 编程题判题流程图
（建议绘制：接收代码→写入临时文件→Docker编译→编译成功？→Docker运行测试用例→结果比对→AI评审→综合判定→输出状态）
```

**（1）Docker 沙箱执行。** 系统通过 `run_java_submission` 函数在 Docker 容器中执行学生代码。执行时调用 `docker run` 命令，添加 `--rm`（用完即毁）、`--network none`（网络隔离）、`--memory` 和 `--cpus`（资源限制）等参数，并通过 `subprocess.run` 的 timeout 参数设置超时时间。编译和运行均在同一镜像环境中完成，保证环境一致性。

编译失败时，系统通过 `_classify_compile_error` 函数分析 stderr 错误信息，将编译错误归类为语法错误、符号解析错误、类型错误等六种类型之一，每种类型映射到候选知识点。例如，错误信息中包含 `cannot find symbol` 的归类为符号解析错误，映射到"变量作用域""方法调用""类与对象"等候选知识点。分类结果写入 results_json 的 error_signal 字段，为教师复核和薄弱点分析提供细粒度诊断信息。

编译成功后，系统逐一运行测试用例，通过标准输入传入测试数据，捕获标准输出并与期望输出进行去尾空白后的精确匹配。每个用例的判题结果包括 case_index、status、passed、input、expected_output、actual_output、elapsed_ms 等字段。所有用例的 passed 均为 true 时为 accepted，否则以第一个失败用例的状态作为整体状态。

**（2）大模型辅助评审。** 系统在沙箱运行结果的基础上调用大模型进行辅助评审。评审提示词将作业标题、题目标题、题目描述、评分标准、测试运行结果、绑定知识点和学生代码组合为结构化输入，要求大模型以 JSON 格式返回 decision、summary、issues、strengths、diagnoses 五个字段。代码如表4-4所示。

表4-4 大模型辅助评审提示词核心结构

```
你是一名严格但克制的 Java 编程作业评审助手。
请根据教师给出的评分标准对学生代码进行保守评审。

作业标题：{assignment_title}
题目标题：{question_title}
题目描述：{prompt}
教师评分标准：{grading_rubric}
题目绑定知识点：{knowledge_nodes}
测试或编译结果：{execution_results}
学生代码：{student_code}

要求：
1. 只返回 JSON 格式数据，不要输出额外解释。
2. decision 只能为 accepted 或 ai_rejected。
3. 不确定时返回 ai_rejected。
4. 需要给出 summary、issues、strengths、diagnoses 字段。
```

大模型评审结果与沙箱运行结果共同决定最终状态。系统根据不同判题模式（testcase / ai_review / hybrid / observed_ai）采用不同的综合策略。例如 hybrid 模式下，沙箱运行通过且大模型评审通过才最终判定为 accepted。

**（3）薄弱点更新。** 判题完成后，若最终状态不为 accepted，系统调用 `_mark_wrong_submission_bound_nodes_weak` 函数更新薄弱点。该函数查询题目绑定的知识点，对每个知识点调用 `mark_node_weak` 进行标记：若该知识点已在薄弱点表中且状态为"unmastered"，则更新 last_seen_at；若此前为"mastered"后又出错，则回退为"unmastered"；若首次出现，则创建新记录。若提交状态为 accepted，则不触发薄弱点更新。

通过上述实现，自动判题模块将代码评测结果映射为学生的薄弱点数据，实现了第3章公式（3-4）定义的诊断逻辑。

### 4.6.4 薄弱点推荐与针对性训练

薄弱点推荐与针对性训练模块将第3章 3.4.2 和 3.4.3 节的方法落地为可交互的学生端功能。

**（1）薄弱点列表与推荐图谱。** 学生进入薄弱点页面后，系统加载当前待掌握的薄弱点列表和历史薄弱点。页面左侧展示待掌握薄弱点，右侧展示当前选中薄弱点的推荐图谱。

学生选择某一薄弱点后，后端调用 Neo4j 查询该节点的 DEPENDS_ON 邻居节点，查询语句如表4-5所示。

表4-5 依赖邻居查询

```
MATCH (target:Knowledge {name: $node_name})-[r:DEPENDS_ON]-(neighbor:Knowledge)
RETURN DISTINCT neighbor.name AS name,
       coalesce(neighbor.desc, '') AS desc,
       type(r) AS relation,
       CASE WHEN startNode(r) = target THEN 'out' ELSE 'in' END AS direction
LIMIT $limit
```

若依赖邻居数量不足，系统以目标知识点名称的关键词在 Neo4j 中搜索匹配节点作为补充，这与第3章 3.5.2 节中图谱检索的关键词匹配机制一致。

后端整合查询结果后，结合学生的知识状态（`UserKnowledgeState` 表）对所有候选推荐节点标记掌握状态：节点已记录为 mastered 的标记为绿色"已掌握"，在薄弱点表中的标记为红色"薄弱"，其他推荐节点标记为橙色"推荐学习"。前端以图谱可视化形式展示薄弱点、推荐节点及其依赖关系。

**（2）针对性出题训练。** 学生点击图谱中的推荐知识点后进入训练流程。后端根据该知识点的名称、描述及相关概念构建提示词，调用大模型生成一道选择题或简答题，提示词限定只返回题目不含答案。学生提交答案后，系统再次调用大模型进行判题，判题提示词包含知识点信息、题目内容和学生答案，要求判断是否正确并给出反馈。

判题后系统更新状态：答对则将薄弱点标记为"mastered"，移出待掌握列表，同时更新 `UserKnowledgeState` 表中对应节点的状态；答错则保持"unmastered"，学生可重新作答。

## 4.7 图谱增强的答疑实现

本节对应第3章知识增强的答疑链路（3.5节）的实现。答疑链路与诊断训练链路数据独立：答疑不修改薄弱点，仅记录提问知识点。

### 4.7.1 大模型连接与流式回答

系统通过 OpenAI SDK 兼容接口连接大模型。配置项包括接口地址（`llm_base_url`）、模型名称（`llm_model_name`）和密钥（`llm_api_key`），统一在 `.env` 配置文件中维护。客户端通过 `lru_cache` 缓存单例，避免每次请求重新创建连接。核心连接代码如表4-6所示。

表4-6 大模型客户端连接

```
from functools import lru_cache
from openai import OpenAI

@lru_cache(maxsize=1)
def get_openai_client() -> OpenAI:
    return OpenAI(
        api_key=settings.llm_api_key or None,
        base_url=settings.llm_base_url
    )
```

系统使用 OpenAI SDK 兼容调用方式，只需修改 base_url 和模型名称即可接入兼容接口的不同大模型服务。

学生发起提问后，前端将问题提交至 `/api/chat/stream` 接口。后端校验用户身份及会话归属后，保存用户消息，然后进入图谱增强答疑流程。整流程由 `stream_message` 函数统一编排，按顺序执行关键词抽取→图谱检索→上下文构建→流式回答→异步知识点记录。流式回答使用 SSE（Server-Sent Events）协议，后端每收到大模型的一个增量分片，将其封装为 `assistant_delta` 事件返回前端，前端实时追加显示。

### 4.7.2 关键词抽取与图谱检索

**关键词抽取。** 系统调用 `extract_keywords_with_llm` 函数，通过提示词要求大模型从学生输入中抽取 Java 知识图谱实体关键词，只返回 JSON 列表。调用时 temperature 设为 0.1 以降低随机性。若返回格式异常，回退为使用用户原始输入作为关键词。

**多阶段图谱检索。** 获得关键词后，系统调用 `query_graph_with_reasoning` 函数完成四阶段检索：

*阶段一（种子节点召回）*：通过 `_query_seed_nodes` 对每个关键词执行分级匹配 Cypher 查询——名称精确匹配得分 4、名称包含得分 3、描述包含得分 2。召回后按 `final_score = 0.55 × match_score + 0.45 × relevance_score` 加权排序，保留得分最高的少量节点作为种子。查询语句如表4-7所示。

表4-7 种子节点分级匹配查询

```
MATCH (n:Knowledge)
WITH n,
  CASE
    WHEN toLower(n.name) = toLower($kw) THEN 4
    WHEN toLower(n.name) CONTAINS toLower($kw) THEN 3
    WHEN toLower(coalesce(n.desc, "")) CONTAINS toLower($kw) THEN 2
    ELSE 0
  END AS match_score
WHERE match_score > 0
RETURN n.name AS name, coalesce(n.desc, "无描述") AS desc, match_score
ORDER BY match_score DESC, n.name ASC
LIMIT $lim
```

*阶段二（子图扩展）*：以种子节点为起点，查询其直接邻居节点和关系边，形成局部子图。同时根据关键词直接匹配部分节点作为补充。

*阶段三（路径枚举）*：在子图内从种子节点出发，通过 DFS 枚举候选路径，搜索深度（max_depth）和分支宽度（width）均有限制。

*阶段四（路径筛选）*：候选路径较少（≤3条）时直接保留；较多时调用大模型选择最能解释问题根因的路径，失败则回退到词汇重叠度排序。最后查询已选路径末端节点的 DEPENDS_ON 依赖链作为补充。

整个检索过程的推理轨迹和检索轨迹分别写入 `reasoning_trace_json` 和 `retrieval_trace_json` 字段，使每轮回答具有可追溯性。

### 4.7.3 上下文构建与回答生成

图谱检索完成后，系统将检索结果、历史对话和学生问题组织为提示词。提示词将大模型设定为 Java 编程辅导老师，要求优先围绕图谱路径解释问题，结合依赖关系说明相关概念，并提示可能需要复习的前置知识。

回答生成调用 `ask_deepseek_stream` 函数，设置 `stream=True`。流式回答结束后，系统拼接所有分片得到完整回答，连同图谱事实（facts_json）、推理轨迹（reasoning_trace_json）和检索轨迹（retrieval_trace_json）一并保存到 `chat_messages` 表中。若图谱检索未获得有效结果，系统回退为直接大模型回答——使用 `_stream_direct_tutor_answer` 函数，仅带入历史对话而无图谱上下文，保证问答不中断。

### 4.7.4 提问知识点异步记录

回答保存后，系统启动后台线程执行 `_run_turn_knowledge_extraction`，异步抽取提问知识点。抽取时，系统将本轮学生问题、大模型回答、上一轮对话上下文以及知识图谱现有节点列表组合为提示词。提示词要求大模型仅从已有图谱节点中选择相关知识点，最多返回 5 个，且每个元素必须包含 `node_id` 和 `node_name`。若本轮对话未明确涉及已有知识点，返回空数组。

大模型返回候选知识点后，系统根据节点编号在 `knowledge_nodes` 表中匹配记录，去重后写入 `chat_knowledge_events` 表。该异步流程不阻塞前端回答展示，也不影响薄弱点状态。提问知识点记录与薄弱点记录分表存储：前者反映学生"问过什么"，后者反映"哪里做错"，共同构成第3章 3.6 节所述的双链路学习数据。

## 4.8 数据看板与学情分析

### 4.8.1 班级数据看板

教师登录后进入数据看板页面，系统展示班级整体学习概况。数据看板后端由 `get_weak_point_dashboard` 函数实现，核心统计指标及数据来源如表4-8所示。

### 4.8.2 学生知识画像

学生知识画像页面帮助教师从个体维度了解学生学习情况。教师可通过班级和姓名筛选学生列表，列表展示每名学生的姓名、班级、当前薄弱点数量和未完成作业数量。

### 4.8.3 作业完成情况查看与人工复核

教师可在作业完成情况页面查看某次作业下所有学生的提交状态。系统按学生和题目维度展示：是否提交、已提交题目数量、最近提交时间、是否逾期以及最终判题状态。后端通过多表联查统计提交情况，将每个学生每道题目的最新提交状态汇总为完成度矩阵。

教师点击某条提交记录后进入详情页，可查看学生提交的代码、测试用例执行结果、运行耗时、大模型评审详情及提交历史。对于编程题，系统保留学生的多次提交记录，便于教师了解修改过程。

考虑到自动判题和大模型评审可能存在误差，系统提供人工复核功能。教师在提交详情中查看判题结果和大模型判定信息后，可将题目标记为通过（accepted）或教师驳回（teacher_rejected），并填写复核备注。后端收到复核请求后，更新提交的 `final_decision_source` 为 `teacher_review`，同步修改提交状态，并记录复核教师、复核时间和复核说明。若教师将之前标记为未掌握的薄弱点对应提交复核为通过，系统同步更新薄弱点状态。

## 4.9 本章小结

本章在第3章双链路方法的基础上，说明了系统的具体设计与实现。基础支撑模块实现了统一身份认证和知识图谱可视化管理，为两条链路提供运行基础。诊断训练链路实现了作业发布与知识点绑定、多题型自动判题、Docker 沙箱安全执行、大模型辅助评审、薄弱点更新、图谱推荐和针对性训练的完整流程。答疑链路实现了关键词抽取、多阶段图谱检索、流式回答生成和提问知识点异步记录。数据看板与学情分析将两条链路的数据汇聚为班级统计、学生画像和作业追溯三个粒度的教师视图。各模块协同实现了从"作业诊断"到"训练巩固"以及从"即时提问"到"回答记录"的双链路辅导功能。
