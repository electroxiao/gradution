# 第3章 融合知识图谱与大模型的编程学习辅导方法

本章说明系统中知识图谱与大模型融合的核心方法。与仅提供单一问答或单一判题功能的系统不同，本系统围绕编程学习场景构建了两条相互配合的服务链路：知识增强的对话交互链路和错题驱动的诊断训练链路。两条链路共享同一套 Java 课程知识图谱作为知识底座，分别解决学生学习过程中"随时想问"和"该练什么"两类需求。

## 3.1 问题形式化定义

在介绍具体方法前，本节先对编程学习辅导场景中的核心概念进行形式化定义。

**定义 1（知识图谱）** 系统知识图谱定义为有向图 \( G = (V, E) \)。其中，\( V = \{v_1, v_2, \ldots, v_n\} \) 为知识节点集合，每个节点 \( v \) 具有属性：名称 \( v.name \)、描述 \( v.desc \) 和所属章节 \( v.chapter \)。\( E \subseteq V \times V \) 为有向边集合，边类型为 \( DEPENDS\_ON \)，表示目标知识点对源知识点的前置依赖关系。例如，边 \( v_a \rightarrow v_b \) 表示学习 \( v_a \) 之前需要先掌握 \( v_b \)。

**定义 2（题目—知识点绑定）** 教师在创建作业时，可为每道题目绑定一个或多个知识图谱节点。题目—知识点绑定关系定义为二元关系 \( B \subseteq Q \times V \)，其中 \( Q \) 为系统题库中的题目集合。若 \( (q, v) \in B \)，则表示题目 \( q \) 考查知识点 \( v \)。

**定义 3（提交状态）** 学生 \( u \) 对题目 \( q \) 的某次提交结果用一个状态值表示，记为 \( status(u, q) \)。状态可能的取值为：\( accepted \)（通过）、\( wrong\_answer \)（答案错误）、\( runtime\_error \)（运行错误）、\( timeout \)（运行超时）、\( compile\_error \)（编译错误）。

**定义 4（薄弱点集合）** 学生 \( u \) 的薄弱点集合 \( W_u \) 定义为：

\[
W_u = \{v \in V \mid \exists (q, v) \in B, \ status(u, q) \neq accepted\}
\]

即：若学生某道题目提交未通过，则该题绑定的所有知识点均为该生的薄弱点。

**定义 5（提问知识点记录）** 学生 \( u \) 在一次对话中涉及的知识点记为 \( K_u^{chat} \subseteq V \)，由系统在回答完成后异步抽取。\( K_u^{chat} \) 仅用于记录学生关注内容，不直接参与薄弱点更新。

基于上述定义，系统的两条服务链路可分别描述如下：

**链路一（对话交互链路）**：给定学生问题文本 \( x \) 和对话历史 \( H \)，系统通过知识图谱检索增强生成回答 \( y \)，并在回答完成后抽取提问知识点 \( K_u^{chat} \)。该链路不修改 \( W_u \)。

**链路二（诊断训练链路）**：给定学生提交的代码 \( c \) 和题目 \( q \)，系统通过沙箱评测得到 \( status(u, q) \)，若未通过则更新 \( W_u \)。围绕 \( W_u \) 中的薄弱点，系统基于图谱生成推荐学习路径，并通过出题训练促使学生掌握对应知识点。当学生答对后，将对应节点从薄弱点中移除。

## 3.2 知识图谱构建与整体方法框架

Java 课程知识图谱是系统两条服务链路的共享知识底座。图谱的构建主要包括资料收集、节点抽取、关系抽取和人工校对四个步骤。首先，根据 Java 课程内容收集公开学习资料和教材等文本材料，并对资料中的重复内容和无关内容进行整理。然后，利用大模型从整理后的课程资料中抽取候选知识点节点，包括知识点名称和知识点描述等信息。例如，从集合相关资料中可以抽取"ArrayList""泛型""集合遍历"等知识点。

在获得候选知识点节点后，将节点列表输入大模型，要求其根据知识点之间的前置关系抽取候选边。例如，如果"数组遍历"的学习需要依赖"循环结构"和"数组下标"，则可以抽取出"数组遍历 —DEPENDS_ON→ 循环结构"和"数组遍历 —DEPENDS_ON→ 数组下标"等关系，表示学生在学习数组遍历前需要先掌握循环结构的基本用法。由于大模型抽取结果可能存在命名不统一、关系方向错误或概念粒度不一致等问题，因此最终写入图数据库前需要进行人工校对。人工校对主要包括统一知识点命名、删除重复节点、调整关系方向、补充缺失描述和筛除不合理关系。经过校对后的节点和关系再导入 Neo4j，作为系统问答、检索和推荐的知识基础。

系统使用 Neo4j 保存 Java 课程知识图谱。图谱中的节点表示 Java 课程知识点，节点标签为 Knowledge。节点属性包括 name（知识点名称）、desc（知识点描述）和 chapter（所属章节）。知识点之间通过 DEPENDS_ON 关系连接，表示知识点之间的前置依赖关系。表3-1给出了知识图谱的结构定义。

表3-1 知识图谱结构定义

| 元素类型 | 名称 | 属性/方向 | 含义 | 说明 |
|---------|------|----------|------|------|
| 节点 | Knowledge | name | 知识点名称 | 唯一标识 Java 编程知识点 |
| 节点 | Knowledge | desc | 知识点描述 | 描述知识点含义 |
| 节点 | Knowledge | chapter | 所属章节 | 支持教师端图谱筛选和作业知识点绑定 |
| 关系 | DEPENDS_ON | Knowledge → Knowledge | 知识点依赖关系 | 起始知识点依赖终止知识点 |

在存储策略上，系统采用 Neo4j 与 MySQL 双存储方案。Neo4j 作为图谱主存储，保存知识点节点及其依赖关系，支持图遍历查询和路径分析。MySQL 中维护一份知识点的引用镜像，仅保存节点名称、所属章节等基本信息，用于作业题目绑定、章节筛选和薄弱点记录等业务场景。教师在教师端图谱维护页面修改图谱后，系统同步更新 Neo4j 中的图数据和 MySQL 中的引用信息。

整体来看，知识图谱在系统中发挥三方面作用。其一，作为对话交互的检索来源——系统根据学生问题抽取出的关键词在图谱中查询相关知识点节点。其二，作为诊断训练的结构约束——系统通过节点关系和依赖路径，为薄弱点推荐学习路径和训练内容。其三，作为统一的知识标识体系——对话记录、作业判题、薄弱点标记等学习行为数据都与同一套知识点体系关联，保证了学习数据的可统计性和可追溯性。

## 3.3 知识增强的对话交互方法

本节说明系统中对话交互链路的实现方法。该链路的核心思路是：在学生提问时，不直接让大模型回答问题，而是先从知识图谱中检索与问题相关的知识点和依赖路径，再将检索结果作为上下文注入大模型，使其生成有明确知识依据的回答。回答完成后，系统异步记录本轮对话涉及的知识点，为学生回看和教师分析提供数据支持。

### 3.3.1 大模型连接与关键词抽取

系统后端通过 OpenAI SDK 兼容接口连接大模型。模型接口地址、模型名称和 API Key 在配置文件中维护，业务代码通过统一客户端调用大模型服务，并使用 LRU 缓存机制避免每次请求都重新创建连接。该调用方式的示例见表3-2。

表3-2 大模型连接示例

```
from functools import lru_cache
from openai import OpenAI

@lru_cache(maxsize=1)
def get_openai_client() -> OpenAI:
    return OpenAI(
        api_key=settings.llm_api_key or None,
        base_url=settings.llm_base_url
    )
```

系统当前使用 OpenAI SDK 兼容调用方式，因此只需要修改 base_url 和模型名称，即可接入兼容接口的不同大模型服务。

在知识增强对话流程中，第一次调用大模型不是为了生成最终回答，而是为了从学生问题中抽取 Java 知识点关键词。学生输入往往不是标准知识点名称，可能包含自然语言描述、代码片段或报错信息。例如，针对问题"为什么我的 ArrayList 取元素时报下标越界"，对应的知识点可能包括 ArrayList、IndexOutOfBoundsException 和集合遍历。

系统通过提示词要求大模型从用户输入中抽取 Java 知识图谱实体关键词，并只返回 JSON 列表。调用时将 temperature 设置为 0.1，目的是降低输出随机性，使关键词抽取结果更稳定。若大模型返回内容不是合法列表，系统会回退为使用用户原始输入作为关键词，避免检索流程中断。该步骤的作用是将自然语言问题转换为图谱查询入口——学生输入不会直接用于查询 Neo4j，而是先经过大模型抽取，得到更接近课程知识点的关键词集合。

### 3.3.2 图谱查询与路径筛选

获得关键词后，系统开始查询 Neo4j 知识图谱。图谱查询分为种子节点召回、局部子图扩展、候选路径枚举和路径筛选四个步骤。该多阶段检索算法（算法3-1）的目标是从知识图谱中筛选出最能解释学生问题的知识路径，而非将所有相关节点都输入大模型。

**步骤一：种子节点召回。** 系统根据每个关键词在 Neo4j 中查询最相关的知识点节点作为种子节点。查询时采用分级匹配策略：名称精确匹配优先级最高（得分 4），名称包含关键词次之（得分 3），描述中包含关键词作为补充（得分 2）。查询语句见表3-3。

表3-3 种子节点查询语句

```
MATCH (n:Knowledge)
WITH n,
  CASE
    WHEN toLower(n.name) = toLower($kw) THEN 4
    WHEN toLower(n.name) CONTAINS toLower($kw) THEN 3
    WHEN toLower(coalesce(n.desc, "")) CONTAINS toLower($kw) THEN 2
    ELSE 0
  END AS match_score
WHERE match_score > 0
RETURN n.name AS name, coalesce(n.desc, "无描述") AS desc, match_score
ORDER BY match_score DESC, n.name ASC
LIMIT $lim
```

召回后，系统对种子节点进行得分融合。每个种子节点的最终得分由匹配得分和问题相关性得分加权计算：\( final\_score = 0.55 \times match\_score + 0.45 \times relevance\_score \)。系统保留得分较高的少量节点作为后续检索的种子。

**步骤二：局部子图扩展。** 获得种子节点后，系统查询与种子节点直接相连的邻居节点和关系边，形成局部子图。该步骤的目的是补充学生问题中没有直接出现但与问题相关的知识点。例如，若种子节点是"数组遍历"，则可能查询到"循环结构""数组下标""数组长度"等邻居节点。在邻居扩展的同时，系统也根据关键词直接匹配部分节点作为补充，并统一按得分排序。子图扩展的查询语句见表3-4。

表3-4 子图扩展查询语句

```
UNWIND $seed_names AS seed_name
MATCH (src:Knowledge {name: seed_name})-[r]-(nbr:Knowledge)
RETURN src.name AS source, type(r) AS relation,
  nbr.name AS target
LIMIT $lim
```

**步骤三：候选路径枚举。** 在得到子图的节点和边集合后，系统从每个种子节点出发，通过深度优先搜索（DFS）枚举从种子节点到子图内其他节点的路径，搜索深度和分支宽度均有限制，避免检索结果过多。每条候选路径表示一条可能的知识解释链，例如：数组遍历 → 数组下标 → 数组越界异常。

**步骤四：路径筛选。** 当候选路径数量较少时（不超过 3 条），系统直接保留全部候选路径。当候选路径数量较多时，系统再次调用大模型进行路径选择。路径选择提示词要求大模型根据学生问题，从候选路径中选出最能解释问题根因、最适合用于教学辅导的路径，并返回路径索引、评分和选择理由。若大模型选择失败或返回格式不符合要求，系统使用本地回退策略——根据学生问题文本与路径文本之间的词汇重叠度进行排序，选择最相关的路径。

路径选择完成后，系统还会围绕已选路径的末端知识点查询 DEPENDS_ON 依赖链，补充该知识点所依赖的底层基础概念。依赖链查询语句见表3-5。

表3-5 依赖链查询语句

```
MATCH path = (target:Knowledge)-[:DEPENDS_ON*]->(root)
WHERE toLower(target.name) CONTAINS toLower($kw)
RETURN path, length(path) AS len
ORDER BY len DESC
LIMIT 3
```

通过上述四个步骤，系统从知识图谱中筛选出与问题最相关的种子节点、已选路径和依赖链，并将这些结构化事实整理为图谱检索结果。

### 3.3.3 上下文构建与回答生成

图谱检索完成后，系统得到一组结构化事实，包括种子节点、候选路径、已选路径、依赖链和相关摘要。这些内容不能直接原样输入大模型，需要先整理为文本化上下文。系统将当前问题、历史对话、图谱检索结果和回答要求组织为统一提示词。提示词将大模型设定为面向学生的 Java 编程辅导老师，要求优先围绕已选图谱路径解释问题，并结合依赖关系说明相关概念和前置知识。图谱增强回答的提示词结构见表3-6。

表3-6 图谱增强回答提示词结构

| 组成部分 | 内容说明 |
|---------|---------|
| 角色设定 | Java 编程辅导老师 |
| 历史对话 | 当前会话最近 6 轮问答 |
| 学生问题 | 本轮学生输入的问题文本 |
| 图谱上下文 | 种子节点 + 已选路径 + 依赖链的文本化表示 |
| 回答要求 | 先回答核心原因、结合图谱路径说明概念关系、提示可能需要复习的前置知识、不直接替学生完成整份作业 |

在回答生成阶段，系统使用大模型流式接口。调用时设置 stream=True，每次从返回分片中读取增量内容，后端将每个增量封装为事件返回前端，前端收到后将文本追加显示。流式返回可以减少用户等待时间，避免必须等完整回答生成后才显示内容。

回答流结束后，后端将所有分片拼接为完整回答，并保存到数据库的消息表中。同时，系统也保存本轮图谱检索得到的事实、推理轨迹和检索轨迹。推理轨迹记录关键词抽取和路径选择的过程，检索轨迹记录 Neo4j 查询和节点召回的情况。这使得每一轮回答都具有可追溯性——学生可以查看回答正文，系统也可以记录回答的依据。

### 3.3.4 提问知识点异步记录

回答保存完成后，系统启动后台异步任务，从本轮问答中抽取涉及的知识点。知识点抽取时，系统将本轮学生问题、大模型回答、上一轮对话上下文以及知识图谱中的现有节点列表组合成提示词。提示词要求大模型仅从已有知识图谱节点中选择相关知识点，不得生成新节点，并规定返回结果必须为 JSON 数组。若本轮对话未明确涉及已有知识点，则返回空数组。

大模型返回候选知识点后，系统根据节点名称在数据库中匹配正式记录，并对同一轮对话中的重复知识点去重，最后写入提问知识点记录表。该步骤与回答生成相互独立，不阻塞大模型流式输出，也不影响前端接收回答内容。提问知识点记录主要用于学生回看历史提问和教师分析提问热点。

需要注意的是，对话交互链路中的提问知识点记录**不直接写入薄弱点表**。学生在问答中提到某个知识点，只能说明该知识点与当前问题有关，不能直接说明学生尚未掌握。薄弱点的识别由下一节所述的诊断训练链路负责。

## 3.4 代码安全评测与多模式判题方法

本节说明诊断训练链路中的第一环节——代码安全评测与判题方法。学生在完成编程作业时提交 Java 代码，系统需要在保障安全的前提下完成代码编译、运行和结果判定，并给出可供薄弱点定位使用的评测状态。

### 3.4.1 Docker 沙箱隔离执行环境

执行学生提交的不可信代码需要采用隔离机制保障宿主系统安全。系统使用 Docker 容器提供代码运行环境，在以下方面实施安全控制：

（1）**网络隔离**：容器运行时添加 `--network none` 参数，禁止容器访问外部网络，防止学生代码发起网络请求或访问外部服务。

（2）**资源限制**：通过 `--memory` 和 `--cpus` 参数分别限制容器的内存和 CPU 使用上限，防止恶意代码耗尽系统资源。

（3）**超时控制**：通过 `subprocess.run` 的 timeout 参数设置代码执行超时时间，超时后自动终止容器进程。默认超时时间为 5 秒，可在系统配置中调整。

（4）**用完即毁**：通过 `--rm` 参数使容器在执行完成后自动删除，不留残留进程。

图3-3展示了 Docker 沙箱执行流程。

具体执行流程如下。系统首先将学生提交的代码写入临时目录的 Main.java 文件，然后通过 `docker run` 调用 `javac Main.java` 进行编译。若编译失败，系统收集编译错误信息并直接返回编译错误状态，不继续运行。编译成功后，系统用 `docker run` 调用 `java Main` 运行程序，通过标准输入传入测试用例数据，同时捕获标准输出和标准错误。若运行过程超时，系统返回超时状态并附带已收集的输出内容。

### 3.4.2 编译错误分类映射

为了将代码评测结果与后续薄弱点定位衔接，系统对编译错误进行了分类映射。当学生代码编译失败时，系统根据错误信息的特征将编译错误归类为不同的错误类型，并将每种错误类型映射到候选知识点。

表3-7给出了编译错误分类与知识点映射关系。

表3-7 编译错误分类与知识点映射

| 错误特征 | 错误类型 | 候选知识点 |
|---------|---------|-----------|
| `';' expected`、`illegal start of expression`、`reached end of file while parsing` | 语法错误（syntax_error） | Java基础语法、语句结束符、代码块结构 |
| `cannot find symbol` | 符号解析错误（symbol_resolution） | 变量作用域、方法调用、类与对象 |
| `incompatible types` | 类型错误（type_error） | 数据类型、类型转换、泛型基础 |
| `non-static variable` 且含 `static context` | 静态实例错误（static_instance_error） | 静态成员、实例成员、main方法 |
| `does not override or implement` | 方法重写错误（override_signature_error） | 方法重写、继承、接口实现 |
| `constructor ... cannot be applied` | 构造方法参数错误（constructor_argument_error） | 构造方法、方法参数、对象创建 |

该映射的作用是将技术层面的编译错误转换为教学层面的知识点提示。当学生代码出现编译错误时，系统不仅能返回编译器的原始错误信息，还能提示该错误可能涉及的知识点。这为后续薄弱点分析和教师了解学生共性错误提供了更细粒度的分类依据。

### 3.4.3 多模式判题策略

系统支持多种判题模式以适应不同的作业场景需求。教师创建题目时可选择合适的判题方式。表3-8列出了系统支持的四种判题模式。

表3-8 多模式判题策略

| 判题模式 | 判题方式 | 适用场景 |
|---------|---------|---------|
| testcase | 仅通过测试用例比对判断，输出精确匹配 | 有明确输入输出的题目 |
| ai_review | 不依赖测试用例，由大模型根据评分标准评审 | 输出形式灵活、不易固化为精确比对的题目 |
| hybrid | 先执行测试用例得到初步结果，再调用大模型补充评审 | 兼顾客观判题与代码质量评估 |
| observed_ai | 沙箱运行后只采集输出，不做比对，将输出和评分标准一起交给大模型判断 | 需要综合评判的开放型题目 |

对于 **testcase 模式**，系统将程序实际输出与期望输出进行严格字符串匹配（去除末尾空白后比对）。若输出完全一致则判定为通过，否则判定为答案错误。若运行超时或返回非零退出码，则分别判定为超时或运行错误。

对于 **hybrid 模式**，系统在测试用例判题的基础上，进一步引入大模型辅助评审。大模型评审时，系统将题目标题、题目描述、评分标准、测试运行结果、绑定知识点以及学生代码组合为结构化的评审提示词，要求大模型以 JSON 格式返回是否通过、问题说明、诊断信息等内容。提示词的结构见表3-9。

表3-9 大模型辅助评审提示词结构

| 输入信息 | 内容说明 |
|---------|---------|
| 题目信息 | 作业标题、题目标题、题目描述 |
| 判题方式 | 判题方式类型、是否启用测试用例 |
| 教师标准 | 教师设定的评分标准和评分关注点 |
| 题目知识点 | 该题绑定的知识图谱节点 |
| 评测结果 | Docker沙箱运行的实际输出、错误信息、耗时 |
| 学生代码 | 学生提交的完整代码文本 |
| 输出要求 | 以 JSON 格式返回 decision、summary、issues、strengths、diagnoses 字段 |

通过上述提示词约束，大模型能够围绕题目要求、测试结果和评分标准进行结构化评审，避免返回自由文本导致后端难以解析。hybrid 模式综合了规则判题的客观性和大模型的理解能力，既能判断代码是否满足功能要求，也能给出代码优点和潜在问题的定性分析。

### 3.4.4 评测结果与薄弱点定位的衔接

无论采用哪种判题模式，系统最终都会为每次提交生成一个确定的状态值。状态可能为 accepted（通过）、wrong_answer（答案错误）、runtime_error（运行错误）、timeout（运行超时）或 compile_error（编译错误）。该状态值将作为下一节所述薄弱点诊断方法的核心输入。评测状态与薄弱点之间的衔接逻辑为：若状态不为 accepted，则触发薄弱点更新流程；若状态为 accepted，则不更新薄弱点。该规则在 3.5.1 节中具体展开。

## 3.5 错题驱动的薄弱点诊断与自适应训练方法

本节说明诊断训练链路中的薄弱点诊断和训练环节。当学生作业提交结果为未通过时，系统依据题目绑定的知识点更新学生的薄弱点记录。在此基础上，系统围绕薄弱点生成图谱推荐学习路径，并通过出题训练促使学生巩固对应知识点。

### 3.5.1 错题—知识点映射规则

学生在完成作业时，每道题目作答后会得到一个提交状态。题目与知识图谱节点之间通过教师在创建题目时建立的绑定关系关联。薄弱点更新规则定义如下：

**规则（错题薄弱点映射）** 对于学生 \( u \) 的某次提交，若提交状态 \( status(u, q) \neq accepted \)，则对于所有满足 \( (q, v) \in B \) 的知识点 \( v \)，将 \( v \) 加入该生的薄弱点集合 \( W_u \)。即：

\[
status(u, q) \neq accepted \implies \forall v \in \{v \mid (q, v) \in B\},\ v \in W_u
\]

实现时，系统查询该题目的知识点绑定记录，遍历所有绑定知识点并将其标记为学生未掌握薄弱点。若该知识点已在薄弱点表中且状态为"未掌握"，则更新其最近识别时间；若该知识点此前被标记为"已掌握"而后又在新的错题中出现，则将状态恢复为"未掌握"；若该知识点首次出现，则创建新的薄弱点记录。

该规则基于教师预先确认的题目—知识点绑定关系，而非让大模型直接判断薄弱点。相比大模型判断方式，教师绑定的知识点关系更加稳定、可解释。教师作为出题人，清楚每道题目考查的知识点范围，因此绑定结果具有教学权威性。

### 3.5.2 图谱驱动的学习路径推荐

学生查看薄弱点时，系统不只是罗列薄弱点列表，而是围绕当前选中的薄弱点，从知识图谱中检索相关知识点，并生成推荐学习路径。

推荐过程分为以下步骤。

**步骤一：查询依赖邻居。** 系统以薄弱点为目标节点，在 Neo4j 中查询与该节点存在 DEPENDS_ON 关系的直接邻居节点。若目标节点依赖于某邻居节点（目标节点出发的 DEPENDS_ON 边指向邻居），则该邻居为目标节点的前置依赖；若某邻居节点依赖于目标节点（邻居出发的 DEPENDS_ON 边指向目标节点），则该邻居为目标节点的后继知识。查询语句见表3-10。

表3-10 依赖邻居查询语句

```
MATCH (target:Knowledge {name: $target_name})-[r:DEPENDS_ON]-(neighbor:Knowledge)
RETURN DISTINCT neighbor.name AS name,
  coalesce(neighbor.desc, '') AS desc,
  type(r) AS relation,
  CASE WHEN startNode(r) = target THEN 'out' ELSE 'in' END AS direction
LIMIT $limit
```

**步骤二：关键词补充匹配。** 若依赖邻居数量不足，系统以目标知识点名称和描述中的关键词为基础，在 Neo4j 中搜索名称或描述包含相同关键词的其他节点作为补充。这与 3.3.2 节中图谱检索的种子节点召回机制类似。

**步骤三：结合知识状态排序。** 系统为每个候选推荐节点计算优先级。排序综合考虑以下因素：该节点与目标薄弱点的关系类型（直接依赖优先于关键词匹配）、该节点当前的学生掌握状态（未掌握的优先于已掌握的）、该节点在 DEPENDS_ON 边上的方向（作为前置依赖的优先于后继知识）。排序后选取优先级最高的若干节点作为推荐知识点。

**步骤四：生成学习路径。** 推荐知识点确定后，系统生成一条有序的学习路径。路径的排列顺序为：先学习推荐的前置依赖节点，再回到目标薄弱点本身。例如，若薄弱点为"数组遍历"，推荐的前置节点为"循环结构"和"数组下标"，则学习路径为：循环结构 → 数组下标 → 数组遍历。

推荐结果输出给前端时包含以下信息：推荐节点列表（含名称、描述、推荐原因）、学习路径顺序、学习建议文本。前端以图谱可视化形式展示薄弱点、推荐节点及其依赖关系，帮助学生理解知识点之间的关联结构。

### 3.5.3 针对性出题训练

学生查看推荐路径后，可选择某个推荐知识点进入针对性训练。系统根据该知识点的名称、描述和相关概念构建提示词，调用大模型生成一道练习题。

出题提示词要求大模型以 Java 编程教学专家的身份，围绕目标知识点生成一道难度适中的选择题或简答题。提示词规定题目必须考查学生对核心概念的理解，且只返回题目内容，不给出答案。若知识点有相关概念补充，提示词中也会一并提供，帮助大模型更准确地把握出题方向。出题提示词结构见表3-11。

表3-11 针对性出题提示词结构

| 组成部分 | 内容说明 |
|---------|---------|
| 角色设定 | Java 编程教学专家 |
| 目标知识点 | 知识点名称和描述 |
| 相关概念 | 与目标知识点相关的其他概念（如有） |
| 出题要求 | 考查核心概念、难度适中、只输出题目不含答案 |

### 3.5.4 训练结果与掌握状态更新

学生提交训练答案后，系统调用大模型进行判题。判题提示词包含目标知识点信息、题目内容和学生答案，要求大模型判断回答是否正确并给出简短反馈。

判题后，系统根据大模型的判断结果更新学生的薄弱点状态：

（1）**答对情况**：若大模型判断学生回答正确，系统将该知识点从薄弱点状态更新为"已掌握"。该薄弱点记录移入历史薄弱点列表，不再出现在当前待掌握薄弱点中。同时，系统的知识状态表中该节点的状态同步更新为"已掌握"。

（2）**答错情况**：若大模型判断学生回答错误，系统保持该知识点的"未掌握"状态不变。学生可以重新查看题目、重新作答，直到答对为止。每次作答的判题反馈信息展示给学生，帮助其逐步理解正确的概念。

该设计使训练过程形成一个小闭环：出题 → 作答 → 判题 → 反馈 → 若未掌握则重新作答，若已掌握则更新状态。学生通过持续训练将薄弱点逐个转化为已掌握知识点。

## 3.6 知识状态驱动的迭代学习闭环

前面各节分别介绍了对话交互链路和诊断训练链路的各个环节。本节从整体视角说明知识状态如何在各环节间流转，形成完整的迭代学习闭环。

闭环的流转逻辑为：学生完成教师发布的作业后，系统通过 Docker 沙箱执行学生代码并进行多模式判题。若某题未通过，系统依据题目—知识点绑定关系将对应知识点标记为该生的薄弱点。学生进入薄弱点页面后，系统基于知识图谱检索相关知识点并生成推荐学习路径。学生选择推荐知识点进入针对性训练，通过出题、作答和判题进行巩固练习。训练答对后，该知识点的薄弱点状态由"未掌握"更新为"已掌握"。状态更新后，学生的当前薄弱点列表自动变化——已掌握的知识点不再出现在待掌握列表中。当学生再次遇到新的作业错题时，新的薄弱点又会被诊断和记录，继续触发推荐和训练流程。

上述过程可以用状态迁移来描述。每个知识点对于学生 \( u \) 有一个掌握状态，状态在三个值之间迁移：

（1）**初始状态**：学生在未经历任何作业和训练时，所有知识点默认为未知状态。该状态下不作为薄弱点展示。

（2）**未掌握（weak）**：当学生作业提交未通过且该题绑定了对应知识点时，该知识点的状态变为"未掌握"，出现在学生的薄弱点列表中。若学生在后续作业中再次答错同一知识点，该状态保持，但最近识别时间更新。

（3）**已掌握（mastered）**：当学生在薄弱点训练中对应该知识点的题目答对后，状态由"未掌握"变为"已掌握"，该知识点从待掌握薄弱点列表中移除，进入历史薄弱点记录。

需要说明的是，知识点状态从"未掌握"到"已掌握"的迁移只能通过针对性训练答对来完成，而不能通过后续作业提交自动完成。即便学生在后续作业中某题答对，系统也不会自动清除之前该题绑定知识点的薄弱点记录。这一设计的原因是：一次作业答对可能包含偶然因素，而针对性训练中围绕特定知识点的出题和回答更能反映学生的理解情况。教师也可以在教学过程中通过人工复核功能对薄弱点状态进行调整。

从数据流动角度看，系统的两条链路在闭环中发挥不同作用。对话交互链路持续记录学生的提问知识点，为教师提供学习关注点的软信号。诊断训练链路追踪学生的错题薄弱点，提供可操作的训练入口。两条链路的数据汇聚在学生端薄弱点页面和教师端学情页面中，使学生能看到自己的薄弱点和提问记录，教师能看到班级的薄弱点热度和提问热点。两类数据的叠加形成了比单一判题系统或单一问答系统更完整的学习过程记录。

综上，系统实现了"作业诊断 → 薄弱点定位 → 图谱推荐 → 出题训练 → 掌握评估 → 状态更新 → 再次诊断"的迭代式学习闭环。该闭环以知识图谱为知识组织基础，以题库—知识点绑定为诊断依据，以针对性训练为巩固手段，在作业、诊断和训练之间建立了数据通路。

## 3.7 本章小结

本章从方法层面阐述了系统中大模型与知识图谱融合的核心思路与关键技术。首先给出了编程学习辅导场景中知识图谱、题目绑定、提交状态和薄弱点的形式化定义，并建立了双轨并行的整体方法框架。

在对话交互链路方面，说明了如何通过 LLM 关键词抽取、多阶段图谱检索（种子召回、子图扩展、路径枚举、路径筛选）和提示词组装，将知识图谱的结构化知识注入大模型回答生成过程，并异步记录提问知识点。

在诊断训练链路方面，说明了 Docker 沙箱的隔离执行策略和编译错误分类映射方法，以及 testcase、ai_review、hybrid、observed_ai 四种判题模式如何适应不同作业场景。在此基础上，阐述了错题到薄弱点的映射规则、基于图谱依赖关系的学习路径推荐算法、针对知识点的出题训练策略以及训练结果驱动的掌握状态更新机制。

最后，从知识状态迁移的角度分析了系统中薄弱点从识别到掌握的完整流转过程，论证了对话交互与诊断训练两条链路如何围绕统一的知识图谱协同工作，形成从作业诊断到训练巩固的迭代学习闭环。
